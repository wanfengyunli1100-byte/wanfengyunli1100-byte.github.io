## 结论先说

在 STM32 这类资源受限的设备上做"周期性状态上报"，UDP 通常比 TCP 更划算：
TCP 的可靠性是有代价的，而这个代价在 MCU 上很难付得干净。

## 代价具体在哪

TCP 要求设备侧维护连接状态：三次握手、序号与确认号、重传定时器、滑动窗口、拥塞控制。
这些都需要 RAM 和代码空间，而且失败路径比成功路径长得多——断线、超时、半开连接，
每一种都要写处理逻辑。

传感器上报这个场景有个特点：**下一条数据很快就来了**。
温湿度每秒采一次，丢一包的直接后果是"这一秒没有数据"，而不是"数据错了"。
既然数据本身是冗余的（下一秒就补上），为它付出全套重传机制的代价就不划算。

## 什么时候 TCP 反而必须用

- **数据不可丢**：比如固件升级包、计费记录、配置下发
- **要穿复杂网络**：多层 NAT、企业防火墙通常只放行 TCP
- **双向长连接**：需要服务端随时推送指令时，TCP 的连接语义更省心

## 实际做法

1. 上报走 UDP，报文带**序号 + 时间戳**，服务端按序号去重和补齐
2. 关键配置走 TCP（或干脆用 HTTP），保证可靠
3. 在 MCU 侧给 UDP 加一个"确认重发"的轻量版本：发出去后等一小段时间，
   没收到服务端的 ACK 就重发一次，最多两次——这不是 TCP，但够用

```c
/* 轻量 ACK 重发：最多 2 次，超时 200ms */
for (uint8_t retry = 0; retry < 2; retry++) {
    udp_send(buf, len);
    if (wait_ack(200) == ACK_OK) break;
}
```

## 一句话

不是"UDP 比 TCP 好"，而是**这个场景不需要 TCP 的那部分可靠性**。
先想清楚丢了这一包会发生什么，答案就出来了。
