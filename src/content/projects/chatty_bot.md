## 做什么

在**只有 4GB 显存的消费级显卡**上，跑通一个能对话、能记事、能调工具的本地桌面助手 ——
不依赖任何云端 API，数据不出本机。

这是整个项目最硬的约束：**硬件不动，让模型适配硬件**。

## 问题：4GB 显存装不下 3B 模型

Qwen2.5-3B-Instruct 直接以 FP16 加载，权重就要约 6GB，加上 KV Cache 与上下文开销，
4GB 卡直接 OOM（显存溢出）。三条路摆在面前：

| 方案 | 为什么不选 / 选 |
|---|---|
| 换更小的模型（0.5B / 1.5B） | 中文指令遵循与工具调用能力明显下降，做不出"助手"的感觉 |
| 一直用云端 API | 与项目目标矛盾（要的就是离线、数据不出本机） |
| **量化 + 微调，把模型压进 4GB** | ✅ 选它 —— 4bit 量化把权重压到约 1/4，剩下的显存留给上下文 |

## 方案：训练在云、推理在端（混合架构）

这是全项目最关键的取舍：**训练和推理分开放在两个地方**。

- **训练**：本地 4GB 卡训不了 3B 模型（训练显存开销远大于推理），
  所以租云端显卡跑 QLoRA —— 只训练低秩适配器（LoRA），不动基座权重
- **推理**：把训练好的适配器合并、量化成 GGUF 格式，落到本地用 Ollama 跑

这样做的代价是多了一条"云端 → 本地"的模型交付链路（合并、转换、量化、导入），
换来的是：**训练用得起，推理跑得动**。

**微调数据**：手写 284 条指令样本，覆盖闲聊、任务管理、工具调用三类场景。
目标不是"让它变聪明"，而是让它**学会这个助手该有的说话方式与输出格式**。

## 怎么做的（三层）

**模型层** —— 284 条指令数据 QLoRA 微调，训练 loss 从 **3.6 收敛到 2.19**，
LoRA 适配器仅 **240MB**，一键加载即用。量化后推理显存占用约 **2.5GB**，单次响应约 **2.5 秒**。

**Agent 编排层** —— 用 n8n 可视化工作流引擎（**12 个核心节点**）串起
`Webhook → 意图分类 / 槽位提取 → Switch 分流（天气 / 提醒 / 闲聊）→ HTTP Request 调外部 API` 的流水线，
**代替传统的 LangChain 代码框架**。取舍很明确：改流程不用改代码，在画布上拖拽即可；
代价是复杂逻辑表达能力不如直接写代码。

**桌面端** —— PyQt6 构建，多线程架构保证 UI 不阻塞主线程。支持聊天对话、
待办任务卡片（倒计时每秒刷新）、对话历史自动持久化、一键深浅主题切换、无边框自定义标题栏。
最终**打包成 exe 交付**，双击即用。

| 编排 | n8n **12 节点**，意图分类 + 槽位提取 + 工具调用流水线 |

## 复盘

1. **"穷显卡"的正解是分而治之**：训练放云端（短时租用按量付费）、推理放本地（长期零成本）。
   把两件事混在一起想，4GB 卡什么都做不了；拆开之后，两边都能跑。
2. **量化的收益是线性的，代价不是**：4bit 把显存压到 1/4，但精度损失要靠微调补回来 ——
   这也是为什么要先微调再量化，而不是直接用量化版基座。
3. **可视化编排的真实价值在迭代速度**：n8n 让"改一次流程"的成本从改代码重新调试，
   降到画布上拖两下 —— 对一个人做全栈的项目，这个杠杆很大。
4. **交付形态决定可用性**：能在自己电脑上跑的 Python 脚本，和双击就能用的 exe 之间，
   隔着"打包"这道很多人不愿做的工序 —— 但它才是"产品"和"练习"的分界线。
