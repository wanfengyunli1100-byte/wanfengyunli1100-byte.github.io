## 做什么

一开始它只是**聚会时发牌的小工具**（PartyCard / 云里发牌助手）：一桌人进房间、翻牌、看规则，
不用再找一副真扑克。后来功能越加越多 —— 游戏、打卡、计分、点单 ——
干脆转型成个人作品集名片「**晚风云里**」，已备案上架。

最终形态是 **21 个页面、三大场景**：聚会游戏、实用工具、商业应用 Demo。

## 规模与构成

| 场景 | 内容 | 说明 |
|---|---|---|
| 聚会游戏（7 款） | 小姐牌、真心话大冒险、谁是卧底、海龟汤、数字炸弹、不要做挑战、你划我猜 | 各带独立规则引擎，其中 3 款走云房间 |
| 实用工具（3 款） | 麻将计分器、微打卡、小决定转盘 | 计分器与打卡依赖云端数据 |
| 商业 Demo | ☕ 咖啡点单（顾客端 + 店主端） | 选品 → 规格 → 购物车 → 下单 → 店主实时看板 |
| 个人与后台 | 首页分类入口、我的（身份管理）、管理员页 | 管理员页可开关游戏、查看用户日志 |

**页面复杂度是分层的**（这份分布来自后来的代码审计）：

| 档位 | 页面 | 量级 | 特征 |
|---|---|---|---|
| 高 | `ladyCard` / `spy` / `mahjong` | 400–550 行 | 云数据库 + watch + 多人状态同步 |
| 中 | `admin` / `checkin` / `coffee/*` | 150–300 行 | 云数据库 CRUD |
| 低 | 6 款纯前端游戏 | 35–292 行 | 数据全在本地，无云依赖 |
| 极简 | 首页 / 列表 / 详情 / 联系 / 我的 | <100 行 | 只负责导航与展示 |

## 架构：五种状态管理模式

这个项目最值得说的不是页面数量，而是**状态管理被收敛成五种模式**，
每个页面必须归入其中一种 —— 看一眼页面属于哪类，就知道它的数据从哪来、要不要处理并发：

| 模式 | 适用页面 | 做法 |
|---|---|---|
| 纯前端本地 | 6 款轻量游戏 | 全部数据在本地，零云依赖（断网也能玩） |
| 云数据库 + **watch 实时** | 小姐牌 / 谁是卧底 / 麻将 / 咖啡店主端 | watch 监听集合变化实时同步，`onUnload` 关闭 watcher |
| 云数据库 CRUD | 打卡 / 管理员 / 咖啡顾客端 | 读写云端，不需要实时性 |
| 缓存驱动 | 「我的」页 | 基于 `wx.getStorageSync('userInfo')`，不每次请求云端 |
| 静态路由 | 首页 / 游戏列表 / 工具列表 / 商业列表 | 只负责导航，无状态 |

**取舍**：能纯前端的绝不连云。6 款游戏因此做到"断网可用、开箱即玩"，
把云资源留给真正需要多人的场景 —— 也顺带绕开了免费版云数据库的并发连接限制。

## 身份与数据流：匿名也能有身份

小程序要识别"你是谁"，但又不想做一套注册登录。做法是**匿名身份链路**：

```
app.js onLaunch
  └→ auth.initUserInfo()
       ├─ 缓存命中 → 直接返回缓存的 userInfo
       └─ 缓存未命中 → wx.login()
                        → 云函数 getOpenId（取 openid / appid / unionid）
                        → 生成匿名 profile（从内置昵称表随机取名）
                        → wx.setStorageSync('userInfo')
```

- 各页面从缓存取 `openid` 当玩家标识：游戏房间靠它认人、打卡靠它当主键、点单靠它写订单
- 「我的」页可改头像 / 昵称（头像上传到云存储 `avatars/{openid}_{timestamp}.jpg`），也能**一键重置回随机匿名**
- 全站只有**一个云函数**（`getOpenId`），其余逻辑全在小程序端

**取舍**：不做账号体系，用一个 openid + 本地缓存解决 90% 的场景；代价是换设备身份会变，
但对"聚会工具 + 作品集名片"来说可以接受。

## 咖啡点单：一次完整的产品化演练

第 14 批加的功能，也是**唯一一个"像商业产品"的模块**：

- **顾客端**：12 款菜单、三组规格（杯型：中杯 / 大杯 +4 元；温度：冰 / 热 / 温；
  甜度：全糖 / 七分 / 半糖 / 三分 / 无糖），选规格**实时重算价格**，
  购物车按"名称 + 规格"合并同类项，提交时取 openid 后写入订单
- **店主端**：当日订单列表（降序 + 状态样式映射）、**watch 监听当日订单**，有新单立刻提醒，
  状态流转：待处理 → 制作中 → 已完成；顶部实时显示今日单量与营业额

**取舍**：菜单硬编码而不上云 —— 因为"改菜单"的频率远低于"下单"，
用改代码换掉一次网络请求与一张表，是划算的。

## 复盘：诚实留下的遗留问题

项目地图里专门有一节"已知注意事项"，这些**没有藏起来**：

1. `coffee_orders` 集合需要**在云数据库里手动创建** —— 否则顾客端下单失败（自动化部署的缺口）
2. `components/` 目录是空的：**全程没用自定义组件**，页面间复用的是 `behaviors` 与全局样式主题
   —— 现在回头看，400+ 行的复杂页面本该拆组件
3. 管理员页**没有用户级入口**（只能手动导航访问）—— 因为它本来就不是给用户看的
4. 小姐牌 / 谁是卧底用 watch，**要留意免费版云数据库的并发连接上限**
5. 开发过程按「设计师出计划 → 操作手改代码 → 检查师出报告」的三角色流程推进，
   并经历过一次微信审核驳回修复（`v2.4.1`：profile 渲染 + 品牌改名 + 3 个页面）
