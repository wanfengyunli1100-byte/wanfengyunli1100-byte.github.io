## 做什么

让房间"自己会动"：温湿度与光照被实时感知，超阈值自动执行（开风扇 / 开灯），
同时还能用自然语言指挥它 —— 说一句话，本地大模型判断这是闲聊还是控制意图，再决定是否下发指令。

**物理世界 → 传感器 → 通信 → AI 决策 → 动作执行**，这条链路整条自己走通。软硬件全栈自研。

## 问题：把"感知 + 决策 + 执行"塞进一套系统

难点不在单个模块，而在它们怎么**分工**又怎么**协同**：

| 难点 | 具体表现 |
|---|---|
| 算力落差 | 大模型跑不进 STM32；而 PC 又碰不到真实的传感器与继电器 |
| 硬件耦合 | 一块板子同时接传感器、屏幕、继电器，任何一处接线错了整块都动不了 |
| 通信可靠 | 无线链路上的数据会丢、会错，直接拿原始字节当指令，很容易误动作 |
| UI 不卡顿 | 串口/无线数据持续到达，若在主线程里同步读取，界面必卡 |

## 方案与取舍：三节点分布式 + PC 端大脑

**取舍一：拆成三块板，而不是一块全功能板。**
采集、显示、控制各一块 STM32，各带无线模块独立工作：
`#1` 采集温湿度与光照并回传；`#2` 在屏上展示系统状态；`#3` 接收指令驱动继电器控制电机（风扇）。

- 换来的：每块板职责单一、**可以分别调试与替换** —— 调试时能精确定位"是采集板错了还是控制板错了"；
- 付出的：节点数量变多、需要一套通信协议与地址管理，系统复杂度从"一块板"上移到"一套网络"。

**取舍二：把 AI 放在 PC，而不是 MCU。**
MCU 负责实时性与确定性（阈值判断、继电器时序），PC 端 Qt 控制中心负责"理解语言 + 做决策"。
算力放在有算力的地方，是这套架构的关键判断。

## 怎么做的

**感知与执行层** —— STM32 节点：`#1` 挂 DHT11 温湿度传感器 + 光敏电阻；
`#3` 通过继电器驱动风扇与灯。除被动响应外，节点侧也有**本地阈值兜底**：
温度 > 28℃ 自动开风扇、光照 < 200 lux 自动开灯 —— 即使 PC 不在线，环境控制也不失效。

**通信层** —— 自定帧格式：**节点 ID + 数据载荷 + 校验字段**，并实现**错误重传**。
裸数据不带地址就无法区分来源，不带校验就无法发现错误，
所以协议设计先于功能开发 —— 这是分布式项目最容易省、也最不该省的一步。

**决策交互层** —— Qt/C++ 控制中心：

- `QThread` 异步读取无线/串口数据，主线程只管 UI；
- **信号槽机制**解耦 UI 与业务逻辑，新增一种设备不用改界面代码；
- 用 **STL 容器**维护多节点设备状态表；
- **观察者模式**在状态变化时自动通知 UI 刷新（而不是定时轮询重绘）；
- 本地大模型同时接受传感器数据与用户聊天输入：判断是闲聊就回应，是控制意图就下发指令。

## 实测与验证

| 项 | 结果 |
|---|---|
| 自动控制 | 温度 > 28℃ → 风扇启动；光照 < 200 lux → 灯光开启（阈值行为实测通过） |
| 通信 | 自定义帧带校验 + 重传，误码不会直接变成误动作 |
| UI | 数据持续到达时界面不阻塞（异步采集 + 观察者通知） |
| 硬件 | 原理图 → PCB 打样 → 焊接调试 → 传感器标定，全流程自己走完 |
| 语言交互 | 同一套模型既能闲聊，也能识别控制意图并下发指令 |

## 复盘

1. **分布式的价值在"可调试性"，不在"技术高级"**：三块板带来的最大好处不是并行，而是
   出问题时能把故障范围缩到一块板；代价是必须先把通信协议定清楚。
2. **协议要带着校验出生**：如果一开始就假设"无线传回来的字节一定是对的"，
   后面每一次误动作都会怀疑到 AI 头上 —— 排查成本会高得离谱。
3. **算力要放在有算力的地方**：把大模型塞进 MCU 是不现实的，
   但把"该由 MCU 做的实时判断"也推给 PC，同样是错的 —— 两层各守住自己的边界。
4. **硬件全流程是最贵的一课**：从原理图到焊接标定，每一步都有"图上看着对、实物不一定对"的坑，
   这也是我后来做 DeskPet 时**把电源链审查写进打样前置条件**的直接原因。
